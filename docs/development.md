# ARGUS Development Guide

How to set up, run, test, and extend ARGUS locally.

## Prerequisites

- Python 3.14+
- Node.js 20+ (frontend)
- Docker + Docker Compose (optional, recommended for the full stack)
- PostgreSQL 16 and Redis 7, **or** just rely on Docker

## 1. Repository layout

```text
apps/api/        FastAPI backend   (Python)
apps/web/        Next.js frontend  (TypeScript)
infrastructure/  Docker & scripts
docs/            Documentation
docker-compose.yml
.env.example
```

## 2. Environment variables

Copy and edit:

```bash
cp .env.example .env
```

Key variables:

| Variable        | Purpose                         | Default                        |
|-----------------|---------------------------------|--------------------------------|
| `DATABASE_URL`  | Async SQLAlchemy URL            | `postgresql+asyncpg://...`     |
| `REDIS_URL`     | Redis connection                | `redis://redis:6379/0`         |
| `API_PORT`      | API bind port                   | `8000`                         |
| `CORS_ORIGINS`  | Allowed web origins (JSON list) | `["http://localhost:3000"]`    |
| `API_ENVIRONMENT` | `development`/`test`/`production` | `development`               |
| `AI_PROVIDER`   | `mock` in Phase 0               | `mock`                         |

Never commit real credentials.

For local API runs, update `DATABASE_HOST`/port to point at your local PostgreSQL or the Docker `postgres` service.

## 3. Run the full stack (Docker)

```bash
docker-compose up --build
```

- Web: http://localhost:3000
- API: http://localhost:8000
- API docs: http://localhost:8000/docs
- Health: http://localhost:8000/health/live

Services start in order: `postgres` and `redis` become healthy, then `api`, then `web`. Both databases use Docker volumes for persistence.

## 4. Run the API locally

```bash
cd apps/api
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt     # runtime + dev (pytest, aiosqlite, ruff, mypy)
cp ../.env.example .env
uvicorn app.main:app --reload
```

With `API_ENVIRONMENT=development`, browse auto-generated docs at `/docs`.

## 5. OpenAPI model

The API is generated by FastAPI from Pydantic schemas. To regenerate/update docs run `python seed_data.py` for demo data (see below). Interactive spec: `http://localhost:8000/openapi.json`.

## 6. Seed data

Deterministic demo data — the **ARGUS Demo Commerce** scenario:

```bash
cd apps/api
python seed_data.py
```

Seed data uses fixed UUIDs (`a0000000-...`, `b0000000-...`), so re-running is idempotent and repeatable. It creates:

- Project: **ARGUS Demo Commerce**
- 7 components: Web Frontend, API Gateway, Checkout Service, Inventory Service, Payment Service, PostgreSQL, Redis
- Environment(s) (production, staging)
- Dependencies: Web → API Gateway → Checkout → {Inventory, Payment, Redis}; Inventory → PostgreSQL; Payment → External Payment API
- Deployments, traces, spans, logs, metrics
- Incident **#1001** — "Checkout latency increased significantly after Inventory Service deployment" with 4 evidence items (deployment, log, metric, trace)

The incident is intentionally presented as **evidence, not root cause**. ARGUS does not declare a root cause in Phase 0.

## 7. Tests

```bash
cd apps/api
pytest
```

168 tests across:

| Module                      | Coverage                                                          |
|-----------------------------|-------------------------------------------------------------------|
| `test_projects.py`          | CRUD, isolation                                                   |
| `test_components.py`        | component CRUD, dependencies                                      |
| `test_observability.py`     | events, logs, metrics, traces, spans, pagination                  |
| `test_incidents.py`         | lifecycle, evidence, 404s                                         |
| `test_deployments.py`       | deployment + repository ingestion                                 |
| `test_ingestion.py`         | normalization pipeline                                            |
| `test_failures.py`          | malformed events, missing parents, invalid values, DB failure     |
| `test_seed_data.py`         | seed idempotency, restart resilience                              |
| `test_phase1_features.py`   | Phase 1 APIs: source registry, health/config events, OTLP (camelCase + snake_case), retention, trace validation, redaction, dead-letter, stats |
| `test_phase1_ingestion.py`  | async queue/worker, retries, backoff, dead-lettering, SAVEPOINT batch isolation |
| `test_phase1_worker_e2e.py` | live worker end-to-end persistence                                |

A live end-to-end smoke gate (`infrastructure/e2e-smoke-phase1.sh`) additionally exercises 46 checks against the running compose stack — sync ingestion, both async drain paths (webhook → Redis → worker and batch queue), OTLP protojson, Prometheus `/metrics`, secret rejection at every ingestion boundary, retention, and the web UI.

Tests use a **file-backed SQLite** database (shared across the TestClient event loop) and truncate all tables before each test for isolation. See `tests/conftest.py`.

Run a single module: `pytest tests/test_observability.py`.

## 9. Database migrations (Alembic)

Migrations live in `apps/api/alembic/` (async engine support).

```bash
cd apps/api
alembic revision --autogenerate -m "describe change"
alembic upgrade head
```

`Base.metadata.create_all()` runs on app startup in development so a quick local run works without migrations; Alembic is the source of truth for schema evolution. In Docker, the API container entrypoint runs `alembic upgrade head` then the idempotent `seed_data.py` before starting uvicorn, so a fresh `docker-compose up` is migrated **and** seeded automatically.

## 10. Run the frontend locally

```bash
cd apps/web
npm install
npm run dev
```

The frontend proxies `/api/*` to the API via `next.config` rewrites (server-side, so the browser never talks to the API directly). The proxy destination is `API_PROXY_TARGET`:

- Local dev: defaults to `http://localhost:8000` — no config needed.
- Docker Compose: set to `http://api:8000` (the compose file does this) so the `web` container reaches the `api` service on the compose network.

## 11. Common recipes

**Reset the local stack**

```bash
docker-compose down -v    # wipes volumes incl. Postgres data
docker-compose up --build
```

**Check dependency health**

```bash
curl -s http://localhost:8000/health/dependencies
```

**Query the system map of the demo scenario**

```bash
curl -s http://localhost:8000/api/v1/projects | jq '.items[0].id'
# then
curl -s http://localhost:8000/api/v1/projects/{id}/dependencies
```

## 12. Style guide (contributors)

- Follow existing module docstrings: `"""ARGUS <Module> — purpose."""`
- Server components first in the frontend; client components only for interactivity
- Never return unbounded lists from the API — use the pagination contract
- Never hardcode a fake architecture diagram — the system map renders dependency data
- Keep AI boundaries separate (see `docs/architecture.md` §7)
